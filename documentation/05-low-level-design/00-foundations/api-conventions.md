# API & WebSocket Conventions — Low-Level Design

## 1. Document Control

| Field | Value |
|---|---|
| Product | Peach Finder |
| Document | Low-Level Design — cross-cutting API/WS conventions |
| Upstream | `shared-kernel.md` (same folder, `UseCaseError`); SRS §5 SR-APP-01/05, §11 SR-SEC-05/06/10 |
| Downstream | Every module LLD's "API" section states only its endpoints/messages and *cites* this document rather than re-deriving envelope/error/pagination rules |
| Status | Living document — updated in place |

Every module LLD's API section is a table of endpoints; this document is what makes those tables unambiguous without repeating boilerplate in all thirteen of them.

---

## 2. HTTP surface shape

- **No `/v1` path prefix.** V1 is the only version; a breaking change to a route ships as a new route or a new field, per the additive-evolution rule in §7. (If a true breaking rewrite is ever needed, that is itself an LLD-level decision at the time, not pre-provisioned for here.)
- **Route grouping mirrors modules:** `/api/<module>/<resource>` for JSON API routes (e.g. `/api/availability/status`), except where a route is a SvelteKit **form action** on a page route (progressive enhancement path, SR-COMPAT-03) — those are documented as `POST <page-route>?/<actionName>` in the module LLD.
- **Admin routes** live under `/admin/api/<module>/<resource>` on the separate admin subdomain (HLD §5, SR-SEC-08) — same envelope and error conventions, different RBAC floor (`role === 'admin'` required at the hook, before any handler runs).

## 3. Response envelope

### 3.1 Success

```json
{ "data": { /* resource or list */ }, "meta": { /* optional: pagination, etc */ } }
```

### 3.2 Error

```json
{ "error": { "code": "REVIEW_INELIGIBLE", "message": "You can review after your conversation is 24 hours old.", "fields": null } }
```

`code` is a `SCREAMING_SNAKE_CASE` string drawn from the enumerated list each module LLD appends to (registered centrally in `event-catalog.md` §5 — errors are catalogued next to events since both are part of the cross-module contract surface). `message` is **always** friendly, plain-language, and safe to render directly to the user (FR-UX-05) — never a stack trace, never raw validation library output. `fields` is populated only for `VALIDATION_FAILED` and mirrors Zod's issue path.

### 3.3 `UseCaseError` → HTTP status mapping

| `UseCaseError.kind` | HTTP status | Notes |
|---|---|---|
| `not_found` | 404 | Also used instead of 403 where existence itself is sensitive (SR-SEC-05 anti-enumeration extends beyond auth — e.g. a blocked user's thread returns 404, not 403) |
| `forbidden` | 403 | Authenticated but not authorized |
| `conflict` | 409 | e.g. duplicate review, already-verified case |
| `validation_failed` | 422 | `fields` populated |
| `rate_limited` | 429 | `Retry-After` header set from `retryAfterSeconds` |
| `unavailable` | 503 | Upstream dependency down (PSP, SMS); route still responds, never hangs |
| `precondition_failed` | 412 | e.g. review thread < 24 h |
| (unauthenticated, no session) | 401 | Raised by the hook before reaching a handler, not a `UseCaseError` variant |
| (uncaught exception / `AuthorizationBug`) | 500 | Logged with correlation ID; body is the generic friendly error, never exception detail |

## 4. Pagination

Cursor-based on every list endpoint (search results, thread list, review list, notification list, admin queues) — offset pagination is disallowed because several of these lists (search projection, message threads) mutate under the reader (SR-PERF-06 freshness bound) and offset drift produces skipped/duplicated rows.

```
GET /api/reviews/provider/:providerProfileId?cursor=<opaque>&limit=20
```
```json
{ "data": [ /* items */ ], "meta": { "nextCursor": "opaque-string-or-null" } }
```

`limit` default and max are declared per endpoint in the owning module LLD (search results and suggestions have tighter caps than, say, billing history). The cursor is an opaque base64 token encoding the sort key(s) of the last item — never a raw offset or raw ID a client could forge to skip access checks; the handler still re-applies row-level authorization/visibility filters on every page regardless of cursor contents.

## 5. Idempotency

- **Admin actions and any POST that changes money/badge/moderation state** accept an optional `Idempotency-Key` header. The handler derives its own idempotency key as `(actor, action, target, key ?? autogenerated-per-request)` and checks `shared.processed_events`-style dedup (module-local table where the action isn't itself an event subscriber — see each module's LLD) before applying. A retried request with the same key returns the original result, not a second execution.
- **PSP webhooks** are idempotent via the provider's own event ID, checked against `listing_billing.processed_webhooks` (billing LLD §4) — never the generic `Idempotency-Key` mechanism, since the caller (Paystack) doesn't send that header.

---

## 6. Rate limiting response contract

Every rate-limited route returns `429` with:
```json
{ "error": { "code": "RATE_LIMITED", "message": "Too many attempts. Try again in a moment.", "fields": null } }
```
and header `Retry-After: <seconds>`. The **mechanism** (unlogged Postgres sliding-window counters, keyed by IP and/or account) is specified in `security-implementation.md` §5; the **concrete bucket table** (which routes, what limits) lives there too as the single source of truth so limits can't drift out of sync across module LLDs.

---

## 7. Versioning & evolution

- **Additive only.** New optional fields may be added to any response without a version bump. Removing or repurposing a field is a breaking change and requires a new field name (old one deprecated, documented, removed on a scheduled cleanup — not silently repointed).
- **Domain events** follow the same rule, stated already in `shared-kernel.md` §6.1: `version: 1` and additive; a genuine breaking payload change ships as a new `eventName`.

---

## 8. Validation error shape

Zod issues are mapped 1:1 into `fields`:
```json
{ "error": { "code": "VALIDATION_FAILED", "message": "Please fix the highlighted fields.", "fields": [ { "path": "email", "message": "Enter a valid email address." } ] } }
```
Field-level messages are the friendly, already-Zod-customized `.message()` text — never the library's default English, which reads as developer-facing.

---

## 9. CSRF

- **Form actions** (progressive-enhancement path): SvelteKit's built-in CSRF origin-check plus a hidden form token, per clean-code-guidelines §7.
- **JSON API routes called from the hydrated app** (fetch, not `<form>`): same-site cookie (`SameSite=Lax`) plus origin header check at the server hook — no separate CSRF token needed for same-origin fetch under `SameSite=Lax`, consistent with OWASP ASVS L2 guidance for this pattern (SR-SEC-06).
- **WebSocket upgrade:** origin header checked at upgrade time; the session cookie (already `SameSite=Lax`, `HttpOnly`, `Secure`) is the auth carrier — no separate WS auth handshake message.

## 10. WebSocket protocol conventions

Applies to the single `web`-process WS endpoint (`/ws`) used by `direct-messaging` (primary consumer) and cross-cutting for live UI updates (e.g. availability-expiry countdown refresh is client-side timer driven, **not** pushed over WS — only messaging state changes ride this channel in V1, keeping the protocol small).

### 10.1 Envelope

```typescript
interface WsEnvelope<Type extends string = string, Payload = unknown> {
  type: Type;              // 'message.sent' | 'message.read' | 'thread.typing' | 'presence.heartbeat' | ...
  payload: Payload;
  sentAt: string;           // ISO-8601 UTC, server-stamped on outbound frames
}
```

### 10.2 Connection lifecycle

1. Client opens `wss://<host>/ws` — browser sends the session cookie automatically (same-origin).
2. Server validates session at upgrade; unauthenticated upgrade is rejected with HTTP 401 before the WS handshake completes (anonymous users never hold a WS connection — messaging requires an account, FR-MSG-01).
3. Server sends `{ type: 'connected', payload: { sessionId } }`.
4. Client sends `{ type: 'presence.heartbeat', payload: {} }` every 30 s; server updates `direct_messaging.presence.last_heartbeat_at` (see `05-direct-messaging`). Missing 2 consecutive heartbeats ⇒ server-side "offline" for presence purposes (SR-APP-06), independent of the socket's own liveness.
5. Reconnection: client uses exponential backoff (1 s, 2 s, 4 s, 8 s, capped 30 s, jittered) — required by SR-APP-05.
6. **Polling fallback** (SR-COMPAT-03): if `WebSocket` construction fails or the connection closes and 3 reconnect attempts fail, the client falls back to `GET /api/messaging/threads/:id/poll?since=<cursor>` on a 4 s interval. The server-side handler code path for new-message delivery is identical either way — the WS push and the poll response are both thin adapters over the same `direct-messaging` query.

### 10.3 Message types (registered per module)

Each module that emits WS messages registers its `type` strings and payload shapes in that module's LLD; `05-direct-messaging` owns the primary set (`message.sent`, `message.read`, `thread.typing`). No module may reuse another's `type` string — the full registry is cross-referenced in `event-catalog.md` §6.

## 11. Server-side privacy filtering (response shaping)

Per clean-code-guidelines §7 and SR-SEC-09: every JSON response is built by a **per-role serializer** function owned by the module whose data it's shaping (e.g. `provider-profile/infra/serializers.ts` has `toPublicProfile(profile, viewerRole)` which omits the phone field entirely when `viewerRole === 'anonymous' && !profile.phoneVisible` — the field is never present on the object, not merely hidden by the client). Every module LLD's API section states, per endpoint, which serializer variant applies to which role. This is the mechanism that makes "field a role shouldn't see is never constructed" (HLD §10.2) true in code, not aspiration.

## 12. Standard headers

| Header | Direction | Purpose |
|---|---|---|
| `X-Correlation-Id` | request → response (echoed) | Propagated into logs, outbox `correlation_id`, and any downstream job — generated at the edge hook if absent |
| `CF-Connecting-IP` | inbound only, trusted only from Cloudflare ranges | Source of `AuthContext.ipAddress` (SR-SEC-03) |
| `Idempotency-Key` | request, optional | §5 |
| `Retry-After` | response, on 429/503 | Seconds |
